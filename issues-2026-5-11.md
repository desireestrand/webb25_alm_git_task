### Dependency notation

Some issues list dependencies so the team can sequence work and PRs:

- **Blocked by:** another issue (or **none**) — you cannot reasonably finish *all* acceptance criteria until the blocker is merged or otherwise satisfied.
- **Partially blocked by:** another issue or external dependency — part of the work can start early (mocks, layout, types), but integration, end-to-end behaviour, or sign-off waits on that dependency.

If a line is omitted, treat it as **none** for that category.

### Add User model and authentication middleware on the backend

**Type:** `enhancement`

**Blocked by:** none.

**Partially blocked by:** none.

Introduce a persisted `User` model and server-side authentication so protected routes can be gated before the frontend auth issue in this file.

**Tasks**

- Define a Mongoose `User` schema with at least `email`, `password` (stored hashed only), and any fields you need for your auth strategy (e.g. `name`).
- Enforce `email` as unique at the schema or application level with clear errors on duplicate registration.
- Hash passwords on create (and when the password is intentionally changed—see the User model test issue in this file for update semantics).
- Implement registration and login (or equivalent) endpoints that issue your chosen credential (e.g. JWT in response or http-only cookie—pick one approach and document it).
- Add authentication middleware that verifies the credential and attaches the user (or user id) to `req` for downstream handlers.
- Apply the middleware to routes that should require a logged-in user (e.g. selected product or category mutations, or a dedicated `/me` route).

**Acceptance criteria**

- Unauthenticated requests to protected routes receive `401` (or your documented status), not `500` from missing auth.
- Passwords never appear in API responses or logs.
- Duplicate `email` registration fails with a predictable client-facing error.

### Add tests for the User model (email, password hashing, selective re-hash)

**Type:** `test`

**Blocked by:** Add User model and authentication middleware on the backend — tests for hashing, login, and “update name without re-hashing password” require the real `User` schema and update path from that work.

**Partially blocked by:** none (if the team agrees on field names early, you may sketch `describe` blocks and fixtures, but keep **Blocked by** in mind before merging tests that assert behaviour not yet implemented).

Cover user persistence and update behavior so regressions around security and uniqueness are caught early.

**Tasks**

- Test that `email` must be unique: creating two users with the same email fails (assert on validation or duplicate key error, depending on implementation).
- Test that stored `password` is never plain text: after create, the value in MongoDB (or the loaded document’s `password` field) is a hash different from the raw password; login still succeeds with the raw password.
- Test that updating a user’s non-password fields (e.g. `name`) does **not** change the stored password hash when the password is omitted from the update payload.
- Test that updating **only** the password produces a new hash and that login works with the new password and fails with the old one.

**Acceptance criteria**

- All of the behaviors above are asserted explicitly in tests (not only implied by manual checks).
- Tests remain stable (no reliance on wall-clock timing except where unavoidable for tokens, if applicable).
